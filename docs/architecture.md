# Архитектура локального pipeline

## Реализовано в PR #2

Пакет `taostats_pipeline` устанавливается через `pyproject.toml`; единственная runtime
зависимость — уже используемый BeautifulSoup. Старые модули не импортируются.
Установка, CLI, manifest и схемы полей приведены в [README](../README.md).

| Этап | Реализация | Ответственность |
| --- | --- | --- |
| Load | `pipeline.local_file`, `run` | Локальные manifest/HTML, проверка путей, inventory ID |
| Parse | `parsers` | Snapshot table, метки metadata, страницы validator metrics |
| Normalize | `parsers.number`, `netuid` | Decimal/integer, явные преобразования, `None` |
| Validate | `validation.validate` | Типы, UTC, числа, уникальность и покрытие ID |
| Export | `exporters` | Шесть CSV/JSON, временный каталог, атомарный указатель |
| CLI | `cli.main` | demo / run / validate, JSON-отчёт, exit code |

Нормализация выполняется при создании моделей, отдельного framework нет.
Модели — неизменяемые dataclass, числа — Decimal (строки в JSON), время из manifest.
Metadata не дублирует emission/price: их источник — snapshot.
Snapshot требует 14 колонок и отдельный ID; метрики — 9 колонок и знакомые SVG-роли.
Неожиданные строки блокируют обработку вместо тихого усечения.
Необязательные поля metadata могут отсутствовать. Пустая таблица метрик — ошибка;
отсутствующая роль даёт `None`. Средний VTrust округляется до 6 знаков.
В строгом режиме отсутствующий итоговый агрегат обязательной роли блокирует экспорт.
Проценты сохраняются в процентных пунктах; денежные префиксы удаляются без
конвертации валют. Значения без единиц не масштабируются.

## Целостность и диагностика

CLI manifest требует непустой уникальный `expected_ids`. Количество подсетей не
используется для генерации диапазона ID. Каждый набор сверяется с inventory;
совпадение трёх наборов обеспечивает связность. API `validate` допускает неизвестный
inventory: сравнивает покрытие с объединением ID всех наборов. Это выявляет
частичный join, но не ID, отсутствующий сразу во всех наборах.

Для каждой записи manifest допускается `expected_metric_pages`: положительный
integer, не boolean. Pipeline сверяет его с длиной списка `metrics` до парсинга.
Несовпадение (как недостаток, так и избыток страниц), некорректный тип или
отсутствующий файл блокируют весь экспорт. Без этого поля сохраняется прежняя
семантика непустого списка. Проверка не доказывает уникальность страниц или
полноту их содержимого и зависит от правильности manifest.

Строгий режим: верхнеуровневый `strict_validation` (JSON boolean, по умолчанию false),
CLI `--strict` / `--no-strict` с приоритетом над manifest, Python keyword `strict`.
`run(strict=None)` использует manifest; `validate` и `export` по умолчанию нестрогие.
При включении обязательны `subnets.emission`, `subnets.price` и все пять полей
метрик: `vtrust_avg`, `incentive_orange_max`, `incentive_orange_min`,
`incentive_green_max`, `incentive_green_min`. Ноль допустим, `None` — ошибка с ID и
именем поля. Остальные необязательные поля остаются необязательными. Это проверка
готовых агрегатов, а не заполненности каждой исходной строки neuron.
Pipeline передаёт выбранный режим также в exporter для повторной проверки.

`ValidationResult`: `status`, `errors`, `record_counts`, `missing_ids`,
`duplicate_ids`, `unexpected_ids`. Проверяются ID, UTC timestamp, конечные Decimal,
неотрицательность обычных показателей и пары min/max. Изменения цены могут быть
отрицательными. Даты регистрации, URL и ключи не проходят внешнюю проверку.
Диапазоны, зависящие от единиц живого сайта, не угадываются.

Pipeline добавляет ошибки загрузки/парсинга в отчёт с категорией и ID для detail
pages. Другие страницы могут оставаться в памяти для диагностики, но при любой
ошибке ни один набор не публикуется. Snapshot возвращается только после разбора
всех строк. Ошибки экспорта меняют статус и exit code. `ERROR` не заменяет данные.

## Публикация файлов

1. Проверить все наборы; exporter дополнительно проверяет вход API.
2. Создать `.staging-*` внутри output (та же файловая система).
3. Записать и закрыть CSV/JSON каждого набора.
4. Переименовать каталог в уникальный `run-*`.
5. Записать временный manifest и заменить `current.json` через `os.replace`.

Точка публикации — шаг 5. Потребитель читает указатель один раз, затем неизменяемое
поколение: отдельные файлы не дают смесь старого и нового запуска. Старые поколения
сохраняются. Флаг `publication_attempted` устанавливается **до** вызова замены
указателя. После этого готовое поколение никогда не удаляется обработчиком очистки:
исключение может возникнуть после фактического `os.replace`, но до возврата из него.
До попытки публикации неопубликованное поколение удаляется, staging и временный
указатель очищаются при обычном завершении обработки исключения.
Если ошибка возникла после фактической публикации, CLI может сообщить ошибку при
уже обновлённом current; новое и предыдущее поколения остаются читаемыми. Отката нет.
При ошибке перед фактической заменой указателя может сохраниться полное поколение,
на которое current не ссылается: при неопределённом исходе выбирается сохранение.
Regression-тесты искусственно выбрасывают OSError, RuntimeError и KeyboardInterrupt
сразу после успешной замены указателя и проверяют все шесть файлов. Сценарии
частичной записи, отказа переименования и отказа до замены current также сохранены.

Нет `fsync`, гарантий при потере питания, блокировок конкурирующих писателей или
автоматической очистки. При конкурентных успешных запусках выигрывает последний
заменивший current. Читатель с сохранённым указателем читает согласованный набор.
После принудительного завершения могут остаться staging/неопубликованные каталоги;
они не считаются current.

## Границы offline-demo

Синтетические подсети 7/42, фиксированное UTC-время, локальные HTML. Содержимое
повторяемо, имя поколения случайное. Нет загрузки URL, браузера, Google-клиента
и чтения credentials. Ссылки из HTML сохраняются как текст.
Принадлежность страниц метрик доверена manifest: таблица не содержит ID подсети.
Без `expected_metric_pages` полнота пагинации не проверяется; с ним проверяется
только число указанных страниц. Дубликаты neuron между страницами не проверяются.
Совместимость с живым Taostats не доказана.

Pytest блокирует TCP, DNS, UDP и создание дочерних процессов. Новые парсеры и demo
проверяются прямыми импортами. Тесты PR #1 сохранены: AST исполняет выбранные чистые
функции, а не старые скрипты. Старая политика пропуска повреждённых строк остаётся
только в legacy-тестах; новый пакет её отвергает. Ruff охватывает новый пакет/тесты;
legacy вне lint. CI запускается на PR без расписания.

## Google Sheets exporter (PR #3)

`exporters/google_sheets.py` — отдельный опциональный exporter. `PipelineResult`
содержит проверенные datasets; `publish-sheets` использует их без промежуточного
CSV/JSON. Остальные команды сохраняют поведение. Повторная проверка моделей перед
сериализацией дополняется проверкой текстовых полей. Заголовки получаются из dataclass.
Строки сортируются по `netuid`; SHA-256 считается по каноническому представлению
таблиц, включая заголовки. Decimal, ID и остальные значения передаются строками.

Dry-run полностью локален: не проверяет Google credentials или удалённую структуру,
не создаёт клиента и листов. `--apply` требует совпадения двух непустых ID, credentials,
доступа и точных заголовков четырёх заранее созданных листов. ID не зашит в Python.
Google imports ленивые, зависимости находятся в extra `google`; scope только Sheets.
Каждая запись, включая retries и журнал ошибок, проходит allowlist-проверку.

Протокол публикации при одном писателе:

1. Проверить вход, конфигурацию, структуру и историю `run_id`.
2. Создать уникальные скрытые staging-листы; записать через `RAW` и прочитать обратно.
3. Одним `spreadsheets.batchUpdate` расширить необходимые сетки, заменить значения
   трёх основных листов через copy-paste и записать строку `success` с SHA.
   Очистка прежних значений входит в тот же batch, что копирование готовых наборов.
   ID и названия основных листов сохраняются. Схема clear → append отсутствует.
4. Прочитать строку журнала и три набора, затем удалить staging одним запросом.

Google [гарантирует атомарное применение операций внутри одного batchUpdate](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/batchUpdate).
Это гарантия шага 3, а не всего протокола. Чтения, staging и очистка — отдельные
запросы; ручные изменения и конкурирующие писатели не изолированы. Основные листы
полностью принадлежат exporter; другие листы не изменяются.

При сбое до шага 3 основные данные сохраняются; возвращается `failed`. После попытки
шага 3 ошибка даёт `partial`, даже если запрос был отклонён или данные уже готовы.
Потерянный ответ проверяется чтением: совпадение полной строки журнала и трёх таблиц
подтверждает публикацию. Финальный запрос не повторяется автоматически. Ошибка проверки
или очистки после подтверждения пытается заменить строку журнала на `partial`.
Неопределённый исход не перезаписывает потенциальный `success`. При недоступном API
локальный отчёт остаётся единственной диагностикой; удалённый журнал может отсутствовать
или содержать `success`, несмотря на локальный exit code 1. Staging при ошибке сохраняется;
его ID приводятся в отчёте как кандидаты для ручной проверки (лист мог не создаться).

Журнал содержит обязательные восемь полей и `data_sha256`. Тот же `run_id` и SHA
с единственной строкой `success` дают исторический no-op; изменённые данные, дубликаты
или другой статус блокируют повтор. Журнал нельзя считать уникальным индексом:
без внешней блокировки два процесса могут одновременно выбрать одну строку.
Exactly-once между процессами не гарантируется; автоматического отката нет.

Чтения и идемпотентный RAW update имеют максимум три попытки с backoff 0.25/0.5 с
для 429, временных 5xx и транспортных ошибок. Остальные записи не повторяются вслепую.
401/403 не повторяются; наружу выходят только безопасные категории ошибок и HTTP-коды.
Тесты используют in-memory API и общий запрет TCP/DNS/UDP/дочерних процессов;
реальные credentials, таблицы и Google-зависимости не нужны.

Настройка и восстановление: [google-sheets-setup.md](google-sheets-setup.md).

## Запланировано, не реализовано

- Сбор HTML отдельным адаптером: таймауты, лимиты, повторы, проверка inventory и
  полноты пагинации. Парсеры остаются независимыми.
- Локальный постоянный журнал запусков и политика хранения поколений.
- Блокировка конкурирующих писателей, автоматическая очистка старого staging.

Ресурсы прежней команды не переносятся. Облако, контейнеры, production deployment
и расписание не являются реализованными возможностями проекта.
